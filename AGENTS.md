# Правила совместной разработки ST-9

Прочитайте этот файл до изменений. Контекст из другой беседы ChatGPT не передаётся
автоматически. Сначала откройте `CONTRIBUTING.md`, `docs/PROJECT_CONTEXT.md` и
`ARCHITECTURE.md`, затем файлы и инструкции по своей задаче. Пользователь может
явно изменить требования; сообщите о существенном расхождении с документацией.

## Ветки и согласование

- Перед работой проверьте `git status`, текущую ветку и последние коммиты.
  Сохраните чужие незакоммиченные изменения. Не используйте для очистки
  `git reset --hard`, `git clean` или принудительную отправку.
- Одна задача — одна ветка от актуальной `origin/main`: `feat/<задача>`,
  `fix/<задача>`, `docs/<задача>` или `chore/<задача>`. Новую задачу не начинайте
  в старой ветке уже объединённого PR. Публикуйте свою ветку и Pull Request.
  Прямые изменения `main`, самостоятельное объединение PR и установка на сервер
  требуют отдельного явного поручения владельца.
- До работы согласуйте задачу с человеком. В Issue/PR перечислите затрагиваемые
  подсистемы. `main.py`, `database.py`, `runtime.py`, `templates/admin.html`,
  общая навигация и установщики часто меняются несколькими разработчиками:
  при пересечении задач согласуйте порядок, не перезаписывайте чужую реализацию.
- Не меняйте заодно критерии наград, права, штрафы, экономику или схемы БД,
  если это не входит в поставленную задачу. Рутинные решения внутри задачи
  принимайте самостоятельно; не запрашивайте подтверждение каждого шага.

## Рабочие данные и внешние действия

- Разрабатывайте на отдельной SQLite-базе с вымышленными игроками. Рабочие `.env`,
  базы, cookies, резервные копии, приватные логи, токены и SSH-ключи не копируйте
  в Git, PR, сообщения или результаты CI. `.env.example` содержит только образец.
- Не подключайте рабочие Discord/SQSTAT/Protocol/BattleMetrics-настройки ради
  тестирования. Фикстуры и подменённые HTTP-ответы уже есть в `tests/`.
  Не добавляйте в приложение публичный обход авторизации для предпросмотра.
- Не отправляйте сообщения/роли в Discord и не запускайте установщики на сервере
  без явного поручения. Наличие кода бота не означает разрешение включить его.
  Не перезапускайте сборщики статистики ради изменения интерфейса.
- Смена схемы, установщик и изменение формата runtime должны учитывать уже
  работающую версию и создавать проверяемую резервную копию. Не восстанавливайте
  рабочую БД автоматически поверх новых записей других процессов.

## Обязательные свойства реализации

- Баланс, финансовая история и состояние игры изменяются атомарно через
  существующий `runtime`/транзакционный путь. Нельзя независимо коммитить кошелёк
  или доверять клиентскому результату игры. Новые расчёты денег — в целых копейках.
- Защитите повторы, параллельные запросы и восстановление после перезапуска.
  Сетевые вызовы не должны удерживать блокировку финансовой транзакции.
- Сохраняйте серверные проверки входа, членства, уровня администратора, CSRF,
  версии состояния и срока действия. Скрытая кнопка не заменяет проверку API.
- Не выдавайте чужие руки/карты, порядок базара, секреты сессий или приглашения
  приватных столов. Пользовательский текст выводите через `textContent` либо
  существующее экранирование. Не ослабляйте CSP для нового скрипта.
- Даты для людей — `Europe/Moscow`; БД и взаимодействие источников — UTC согласно
  существующим соглашениям. Отсутствие данных/покрытия не доказывает прогул.
- Сохраняйте тёмную тему, телефонное управление и русские подписи. Пишите
  многострочный читаемый JS; большие блоки выносите в понятные partial-шаблоны.
  Для массовых записей сохраняйте предварительный просмотр и одноразовое
  подтверждение точного плана. Договорённости предметной области — в
  `docs/PROJECT_CONTEXT.md`; детали авторитетны в коде и его тестах.

## Проверка и результат

- Выполните `bash scripts/check.sh` в отдельном окружении разработки. Он проверяет
  Python, shell и запускает `tests/`, включая синтаксис отрисованного JavaScript.
  Для разработки нужны Python 3.12 и Node.js. На промежуточных итерациях можно
  запускать только относящиеся к изменению тесты; перед PR выполните общий набор.
- Изменения денег, прав, миграций и игровых правил требуют проверки существенных
  сценариев отказа/повтора. Для низкорисковой вёрстки достаточно проверки страницы
  и уместных существующих тестов. Не создавайте формальные тесты ради количества.
- Управление мышью/касанием проверяйте в браузере. Для домино есть отдельный
  `scripts/check_domino_drag.py`; Playwright не является зависимостью сервера.
- В PR опишите итоговое поведение, выполненные проверки, совместимость и порядок
  установки. Явно отделите локальную проверку от проверки настоящих источников
  или установки на сервер. Не утверждайте, что задача развёрнута, по одному push.
- Обновляйте документацию по изменённой подсистеме. Число тестов и доступность
  внешних источников указывайте по фактическому запуску.
