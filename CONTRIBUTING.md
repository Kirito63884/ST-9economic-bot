# Совместная разработка

Репозиторий: https://github.com/Kirito63884/ST-9economic-bot.
Рабочее приложение и бот используют общую базу. Изменения сначала проверяются
в отдельной среде и Pull Request, затем владелец решает, когда устанавливать их.

## Первое подключение знакомого

1. Владелец открывает репозиторий → **Settings → Collaborators → Add people**
   и приглашает отдельный GitHub-аккаунт знакомого. Приглашение нужно принять.
   Для личного репозитория collaborator получает право записи; права владельца
   или общий пароль от аккаунта для разработки не нужны.
2. Знакомый подключает свой GitHub в ChatGPT/Codex, используя свой аккаунт, и
   выбирает этот репозиторий. Если репозитория нет в списке, проверьте принятое
   приглашение и настройки доступа установленного GitHub-приложения. Доступ к
   чтению в обычном чате сам по себе не даёт среду, способную изменять и отправлять
   код: для работы нужен Codex либо другое подключение с записью веток и PR.
3. В его отдельную рабочую среду клонируется репозиторий. Ему передаётся
   [готовый текст для помощника](docs/CHATGPT_HANDOFF.md), затем конкретная задача.
   Пароли, `.env`, рабочая БД и доступ root для этого не требуются.
4. После установки файлов этой подготовки в `main` включите защиту ветки,
   описанную ниже. GitHub-приглашение и защита — отдельные настройки сервиса:
   наличие файлов в Git само по себе их не включает.

## Проверяемое окружение

Python **3.12**, Node.js **22** (используется `node --check`), Bash и Git.
Зависимости закреплены в `requirements-dev.txt` и `requirements.txt`.

```bash
git clone https://github.com/Kirito63884/ST-9economic-bot.git
cd ST-9economic-bot
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
bash scripts/check.sh
```

В Windows те же Bash-команды запускайте в WSL или Git Bash; создание venv можно
выполнить командой `py -3.12 -m venv .venv`, активацию в PowerShell —
`.\.venv\Scripts\Activate.ps1`. Команды Bash нельзя без изменений вставлять в CMD.

Для тестов `.env` не нужен: `tests/conftest.py` создаёт отдельные временные базы,
тестовые сессии и пользователей. Общая команда проверок отключает чтение `.env`.
Не запускайте тесты из рабочей установки сайта и не передавайте production
credentials в среду разработчика.

Для локальной стартовой страницы можно скопировать `.env.example` в `.env`,
задать свой случайный `SECRET_KEY` и выполнить:

```bash
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Получится отдельная dev-база. Рабочий Discord-вход без собственных настроек
интеграции недоступен. Авторизованные страницы проверяйте существующими фикстурами
и TestClient; открытый dev-login в приложение добавлять не нужно. Не запускайте
`discord_bot.py` или сборщики с рабочими настройками ради предпросмотра.

## Порядок каждой задачи

1. Владелец назначает конкретную задачу одному разработчику. Можно использовать
   Issue с шаблоном «Задача»: цель, границы, затрагиваемые файлы и критерии готовности.
   Другой помощник не видит вашу переписку; договорённости записывайте в Issue/PR.
2. Из чистой рабочей копии получите актуальный `main` и создайте свою ветку:

   ```bash
   git fetch origin
   git switch -c feat/short-task-name origin/main
   ```

3. Прочитайте `AGENTS.md`, контекст и код. При пересечении по общим файлам
   согласуйте порядок с другим разработчиком. Не храните две рабочие среды
   на одном серверном каталоге; у каждого свой checkout/окружение.
4. Сделайте изменения и выполните `bash scripts/check.sh`. Для взаимодействий
   добавьте проверку браузера; для домино отдельно доступен Chromium-runner.
5. Отправьте ветку и откройте PR в `main`. Шаблон PR уже включён:

   ```bash
   git push -u origin feat/short-task-name
   ```

6. Второй человек просматривает diff и результаты CI. Автор не утверждает свой PR.
   После новых изменений старое одобрение сбрасывается. Конфликты решайте в ветке
   задачи, сохраняя обе согласованные функции, затем повторяйте уместные проверки.
7. Владелец объединяет PR, предпочтительно **Squash and merge**. Для новой задачи
   снова берётся свежий `origin/main`. Установка на сайт выполняется отдельно.

## GitHub Actions и защита main

`.github/workflows/checks.yml` запускает job **checks** для PR в `main`, push в
`main` и вручную. Используется обычный `pull_request` с `contents: read`, без
production secrets, выдачи ролей, начислений или установки на сервер. Проверки
не стартуют на GitHub, пока workflow не попадёт в ветку события/PR и Actions
не будут разрешены в настройках репозитория.

После первого успешного PR-проверочного запуска владелец открывает:

**Settings → Branches → Add classic branch protection rule**, pattern `main`:

- Require a pull request before merging → **1 approval**;
- Dismiss stale pull request approvals when new commits are pushed;
- Require approval of the most recent reviewable push;
- Require status checks to pass → **checks**, Require branches to be up to date;
- Require conversation resolution;
- Require linear history (используйте Squash and merge или Rebase and merge);
- Do not allow bypassing the above settings (применять к администраторам);
- Allow force pushes и Allow deletions выключены.

`CODEOWNERS` запрашивает проверку владельца, но сам не запрещает объединение.
Обязательна одна проверка другого человека; обязательный code-owner review
отключён, чтобы владелец мог отправить свой PR на проверку знакомому.

Тот же набор настроек сохранён в `.github/branch-protection.json`. Владелец с
GitHub CLI и достаточными правами может выполнить вместо настройки через UI:

```bash
gh auth login
bash scripts/configure_github_collaboration.sh
```

Скрипт проверяет включённость Actions, затем применяет защиту только `main` и
проверяет ответ GitHub. Он не приглашает пользователей, не меняет видимость
репозитория, не устанавливает сайт и не запрашивает токен в сообщении чата.
Ключевые опции идемпотентны. Перед применением просмотрите JSON: существующая
классическая защита будет заменена этим набором, дополнительные rulesets остаются.

Для частного репозитория защита может требовать платного тарифа GitHub. Если API
отвечает, что функция недоступна по тарифу/правам, не считайте защиту включённой.
Не меняйте видимость репозитория ради её включения без решения владельца.
До включения технической защиты соблюдайте тот же PR-порядок вручную.

## Установка и проверки после неё

После объединения владелец выбирает полный SHA из `main` и относящийся к
подсистеме установщик в `scripts/`. Старый установщик может перечислять только
часть новых файлов: изменение whitelist и совместимость входят в задачу автора.
Просто `git pull` в рабочем каталоге или копирование одного `main.py` не являются
универсальным способом установки.

Перед изменением рабочих файлов нужна проверенная приватная резервная копия.
При изменении шаблонов обычно достаточно сайта; сборщики SQSTAT и игрового
онлайна перезапускаются только по необходимости конкретной задачи. Проверяются
HTTP, журнал нужного сервиса и затронутые действия под нужными ролями.
Коммит в GitHub, зелёный CI и статус сервиса `active` не подтверждают все функции
или доступность внешних источников.
