# Обновление: массовые операции, свежесть статистики и защита запросов

## Что изменилось для пользователей

### Массовые операции

В админке перед массовым начислением, списанием, сохранением изменённых балансов,
начислением по Steam ID и импортом открывается предварительный просмотр.
Он показывает игроков, старый баланс, изменение, новый баланс, другие поля импорта,
общую сумму, количество пропущенных записей, некорректные и не найденные Steam ID.
До подтверждения пользовательские данные и финансовая история не изменяются.

Подтверждение действует пять минут и подходит только выдавшему его администратору,
исходному адресу и содержимому операции. Если данные изменились, потребуется новый
просмотр. Повторная отправка уже использованного подтверждения отклоняется.
Массовые операции ограничены 1000 входными записями; дубли в импорте и установке
балансов отклоняются. Повторные ID получателей при начислении объединяются.

Начисления за онлайн Squad уже имели отдельный механизм предпросмотра; он сохранён.

### Свежесть статистики

В общей навигации и админке есть раскрываемый блок «Свежесть статистики».
Он показывает успешное обновление источников по московскому времени, отсутствие
данных, устаревание и состояние последней проверки. Неудачная попытка обновления
не делает старые сведения свежими. Выгрузки Protocol показываются отдельно по
периодам и категориям, чтобы успех одной категории не скрывал сбой другой.

Пороги отображения: Protocol — 24 часа, статистика матчей SQSTAT — час,
голосовая активность Discord — две минуты, онлайн BattleMetrics — 90 секунд.
Это показатели интерфейса, а не новые основания для штрафов или выдачи наград.
Закрытые недели остаются историческими доказательствами.

### Два знака отличия

На странице https://protocol-squad.ru/clan/achievements?clan=STRIKE%20TEAM%209#dumps:

- Первое место завершённой недели в разделе «Пилот — топ-3 недели
  (пилот и командир вертолёта)» — основание для «Лучшего пилота».
- Первое место завершённой недели в разделе «Экипаж — топ-3 недели
  (экипаж и командир экипажа)» — основание для «Лучшего мехвода».
- Второе и третье места этих таблиц не дают соответствующий знак.
- Текущая, ещё незавершённая неделя не даёт знак.
- «Лучший экипаж» сохраняет прежний критерий по недельному урону.

Имена не используются для идентификации: проверяются Steam ID, заголовок,
единицы измерения, период и совпадение страницы с TXT-выгрузкой. Сохраняется
существующее утверждение недельных наград главным администратором.
Старое условие 50 часов для автоматической выдачи «Лучшего пилота» удалено.
Уже выданные знаки автоматически не отзываются и не оплачиваются повторно.

Из облачной среды Protocol ответил HTTP 403. Парсер и правила проверены на
сохранённом формате страницы и синтетических новых таблицах, не на живой
авторизованной выгрузке. На сервере используется существующая сессия Protocol;
после установки нужно проверить новые категории в разделе выгрузок админки.
Если реальная страница не соответствует проверяемому формату, выдача блокируется.
Не передавайте cookies Protocol или токены в чат.

## Изменения безопасности

1. Для авторизованных изменяющих запросов введён случайный CSRF-токен сессии.
   Формы и same-origin fetch-запросы передают его автоматически. Проверки
   Origin сохранены, а при отсутствии Origin проверяется Referer.
   Вход по одноразовой ссылке сохраняет собственную CSRF-проверку и CSP с nonce.
2. Подтверждение массовой операции проверяется на сервере, а не только в окне
   браузера. Оно привязано к пользователю, данным и плану изменений, используется
   один раз и сохраняется атомарно с изменением баланса.
3. Предпросмотр выводит введённые имена и поля через textContent.
4. Защита от встраивания страниц во фреймы: X-Frame-Options и CSP frame-ancestors.
   Также добавлены nosniff, ограничение browser permissions, защита base-uri
   и object-src. Это не полная CSP для всех скриптов: старые inline-обработчики
   событий в интерфейсе пока остаются.
5. Динамические страницы и ответы не кэшируются. Существующие private/no-store
   заголовки и более строгая CSP страницы входа сохраняются.
6. Cookie автоматически получает Secure, если публичный адрес HTTPS и
   COOKIE_HTTPS_ONLY явно не задан. Явная настройка окружения имеет приоритет.
7. Результаты рулетки, тасование и Crash используют SystemRandom ОС вместо
   предсказуемого генератора random. Это не система provably fair.
8. GET /logout теперь показывает подтверждение. Выход выполняется POST с CSRF.

Проверялись исходники и локальная копия приложения. Системные службы, Nginx,
TLS, доступы к серверу и реальные секреты этой проверкой не охвачены.

## Читаемость и сопровождение

Python отформатирован Ruff. HTML, CSS и встроенный JavaScript развёрнуты
в многострочные блоки с отступами. Новая логика выделена в bulk_operations.py,
statistics_freshness.py и http_security.py; структура описана в ARCHITECTURE.md.
Документация прежнего README описывает более раннюю версию: новые критерии
наград и команды обновления смотрите в этом файле.

## Установка на сервер

Обновление подготовлено как архив исходников. На сервер оно автоматически
не устанавливалось. В архиве нет .env, рабочей БД, cookies, venv и squad-data.
Не создавайте новую базу вместо существующей.

1. Скачайте архив из чата на компьютер. Загрузите его на сервер, например:

   ```text
   scp balance-app-updated.tar.gz root@132.243.125.99:/tmp/
   ```

2. На сервере распакуйте в отдельную временную папку:

   ```bash
   mkdir -p /tmp/balance-app-update
   tar -xzf /tmp/balance-app-updated.tar.gz -C /tmp/balance-app-update
   ```

3. Определите имена системных служб сайта, бота и сборщиков. Остановите службы,
   работающие с этой папкой/базой, на время резервного копирования и обновления.
   Их названия в архиве не указаны, поэтому не подставляйте выдуманные имена.

4. Сделайте резервную копию ВСЕЙ существующей папки после остановки процессов.
   Например, под root:

   ```bash
   umask 077
   tar -czf "/root/balance-app-before-update-$(date +%Y%m%d-%H%M%S).tar.gz" -C /var/www balance-app
   ```

   Эта серверная резервная копия содержит секреты и БД: храните её приватно,
   не отправляйте в чат. Для внешней БД нужен её отдельный согласованный backup.

5. Скопируйте исходники без удаления существующих локальных данных:

   ```bash
   cp -r /tmp/balance-app-update/. /var/www/balance-app/
   ```

   Архив нормализован: файлы 0644, каталоги 0755. Новые файлы должны читаться
   пользователем службы, обычно www-data. Не меняйте права .env и app.db.
   Зависимости приложения не изменены; новый pip install обычно не нужен.

6. Запустите прежние службы сайта, бота и сборщиков. При старте создаётся только
   дополнительная таблица bulk_confirmations для временных подтверждений.
   Остальные изменения схемы — прежние миграции приложения.

7. Откройте сайт с полной перезагрузкой страницы. Проверьте предпросмотр и отмену
   операции на тестовом аккаунте, свежесть источников, вход и данные Protocol.
   Старые открытые вкладки могут получить 403 до перезагрузки из-за нового CSRF.

8. Если используются собственные API-клиенты, обновите их: для запросов с сессией
   нужен CSRF-токен, для четырёх массовых endpoint — preview=true, затем заголовок
   X-ST9-Confirmation с полученным подтверждением. См. тесты как примеры.

Для отката остановите те же службы и восстановите согласованную резервную копию.
Учитывайте: восстановление старой БД отменит операции, сделанные после её создания.

## Проверки

Запуск из корня проекта на Python 3.12:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q tests
python -m ruff check . --select E9,F
```

Для tests/test_frontend_scripts.py нужен Node.js. Без него проверка синтаксиса
браузерных скриптов будет явно пропущена. Реальные Discord/Protocol в тестах
не используются. Результаты итогового запуска прилагаются в VALIDATION.txt.
